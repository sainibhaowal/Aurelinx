# Aurelinx Infrastructure

Production-grade Docker and deployment infrastructure for the **Aurelinx Executive Talent Intelligence Platform**.

This directory contains everything needed to run the full stack — PostgreSQL, Redis, Qdrant, FastAPI backend (API + worker + scheduler), and the Next.js frontend — locally with Docker, or deployed to production via the automated CI/CD pipeline.

---

## Architecture at a glance

```
                         ┌───────────────────────────────┐
                         │  Shared Caddy gateway (VPS)   │
                         │  /opt/gateway — ports 80/443  │
                         │  TLS + reverse proxy          │
                         └──────┬───────────────┬────────┘
                                │ /api/*        │ everything else
                                ▼               ▼
                         ┌────────────┐   ┌────────────┐
                         │  api:5000  │   │  web:3000  │
                         │  FastAPI   │   │  Next.js   │
                         └─────┬──────┘   └────────────┘
                    ┌──────────┼──────────┐
                    ▼          ▼          ▼
              postgres    redis        qdrant
              (SQL data)  (cache)   (vector data)
```

- **Production**: images are pulled from **GitHub Container Registry (GHCR)** — no source code is built on the server.
- **Local development**: everything is built and run with a single compose command.
- **TLS**: handled by a shared Caddy instance on the host (`/opt/gateway`), which routes both `averqel.com` and `aurelinx.averqel.com`.

## Repository layout

| File / directory | Purpose |
|---|---|
| `docker-compose.prod.yml` | Production stack — image-only services (no `build:` lines), reads `./.env.production` |
| `docker-compose.local.yml` | Local development stack — builds images from source, reads `./.env.local` |
| `backend.Dockerfile` | FastAPI image — installs deps, runs `alembic upgrade head`, starts Uvicorn on `:5000` |
| `frontend.Dockerfile` | Next.js standalone production image (Node 20) |
| `.env.local` | Local development secrets (generated by `server/scripts/generate-env-local.sh`) |
| `.env.production.example` | Template for the production environment file (copy → `.env.production` on the VPS) |
| `postgres/init/001-init.sql` | PostgreSQL bootstrap script (runs once on first volume creation) |
| `manage-codes.sh` | Helper for managing registration/admin codes |

> **Note:** the standalone `Caddyfile` was removed from this stack — a shared Caddy gateway on the host handles TLS and routing for production. For local development, `docker-compose.local.yml` includes its own Caddy.

## Services

| Service | Image / Build | Port (host → container) | Purpose |
|---|---|---|---|
| `postgres` | `postgres:16-alpine` | `55433 → 5432` | Primary relational database (schema `app`) |
| `redis` | `redis:7-alpine` | `6380 → 6379` | Cache, queues, SSE pub/sub |
| `qdrant` | `qdrant/qdrant:v1.13.6` | `6335 → 6333` (HTTP), `6336 → 6334` (gRPC) | Vector database for embeddings |
| `api` | `ghcr.io/sainibhaowal/aurelinx-backend:<ver>` | `5100 → 5000` | FastAPI REST API |
| `worker` | same backend image | — | Async background jobs (`scripts/retry_worker.py`) |
| `scheduler` | same backend image | — | Lean scheduler (`scripts/retry_scheduler.py`) |
| `web` | `ghcr.io/sainibhaowal/aurelinx-frontend:<ver>` | `3100 → 3000` | Next.js frontend |
| `caddy` *(local only)* | `caddy:2-alpine` | `80`, `443` | Local TLS / reverse proxy (dev convenience) |

**Volumes** (named, preserved across deploys): `postgres_data`, `redis_data`, `qdrant_data`, `chat_uploads`.

## Local development

### Prerequisites

- Docker Engine 24+ with the Compose plugin
- `bash` (for the env generator script)

### 1. Generate local secrets

```bash
bash server/scripts/generate-env-local.sh
```

This creates `infra/.env.local` with strong random secrets for Postgres, Redis, and JWT.

### 2. Start the stack

```bash
cd infra
docker compose -f docker-compose.local.yml --env-file .env.local up -d --build
```

### 3. Verify

| Endpoint | URL |
|---|---|
| Frontend | http://localhost:3100 |
| API docs (Swagger) | http://localhost:5100/docs |
| Health check | http://localhost:5100/health |

```bash
curl -s http://localhost:5100/health | jq .
# {"status":"healthy","service":"aurelinx","version":"...","environment":"development"}
```

### 4. Stop

```bash
cd infra
docker compose -f docker-compose.local.yml --env-file .env.local down
```

> Add `-v` to also delete named volumes (⚠️ wipes local data).

## Production deployment

The production stack is **image-only**: it pulls prebuilt images from GHCR. Builds and deploys are handled automatically by the GitHub Actions pipeline (`.github/workflows/release.yml` in the repo root) whenever a `v*` tag is pushed.

### Production environment file

Create `.env.production` from the template:

```bash
cp .env.production.example .env.production
```

**Two critical rules** (both were hard-learned failures):

1. `DATABASE_URL` password must be **identical** to `POSTGRES_PASSWORD` — a mismatch causes `password authentication failed` and an unhealthy API container.
2. `ALLOWED_HOSTS` must include `localhost,127.0.0.1` — otherwise the internal Docker health check is rejected (`400`) and the container is marked unhealthy.

### Deploy flow (automatic)

```
git tag vX.Y.Z → GitHub Actions:
  1. build-and-push  → builds backend + frontend, pushes to GHCR (version + latest tags)
  2. deploy          → SSH to VPS → docker login (GHCR_PAT) → compose pull
                      → compose up -d --wait → health check → prune old images
```

No manual commands are needed on the server after the initial setup.

## Health checks

Every service defines a Docker health check. The API's health endpoint is exempt from the HTTPS-enforcement middleware, so the internal health check works over plain HTTP:

```bash
curl -s http://localhost:5100/health | jq .
```

Expected in production:

```json
{
  "status": "healthy",
  "service": "aurelinx",
  "version": "1.1.15",
  "environment": "production",
  "timestamp": "..."
}
```

## Troubleshooting

| Symptom | Cause | Fix |
|---|---|---|
| `pull access denied ... repository does not exist` | compose image missing `ghcr.io/` prefix, or VPS login uses the workflow `GITHUB_TOKEN` | add `ghcr.io/` to image lines; use a PAT with `read:packages` (secret `GHCR_PAT`) |
| `password authentication failed for user "aurelinx"` | `DATABASE_URL` ≠ `POSTGRES_PASSWORD`, or stale Postgres volume | make passwords identical; recreate the volume for a fresh DB |
| container `unhealthy`, `/health` returns `400` | `ALLOWED_HOSTS` missing `127.0.0.1` | add `localhost,127.0.0.1` to `ALLOWED_HOSTS` |
| API reports `"version": "1.0.0"` | `api` service missing `VERSION` env | add `VERSION: ${VERSION:-1.0.0}` to the `api` environment |
| `ERR_NAME_NOT_RESOLVED` for `api.*` subdomain | frontend built with an API URL that has no DNS record | use the main domain in `NEXT_PUBLIC_API_URL` (Caddy routes `/api/*`) |

## Maintenance

Safe cleanup (keeps all volumes / data):

```bash
docker image prune -af     # old unused images (done automatically after every deploy)
docker builder prune -af   # build cache
```

⚠️ Never run `docker volume prune -f` or `docker system prune -af --volumes` unless you intend to destroy the database.
